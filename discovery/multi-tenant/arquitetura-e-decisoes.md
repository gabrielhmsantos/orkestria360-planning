# Arquitetura e decisões

## Entra ID, consentimento e credencial

1. Alterar a App Registration existente para `AzureADMultipleOrgs` (portal: **Accounts in any organizational directory**). Não selecionar contas pessoais: daemon app exige admin de diretório organizacional para conceder Application Permissions.
2. O application object continua apenas no tenant de origem do Orkestria; cada organização conectada recebe um service principal, exposto no portal como Enterprise Application. O service principal local armazena o consentimento e configurações locais; não é uma cópia de app registration.
3. Application Permissions permanecem app-only e são concedidas ao service principal do tenant cliente. Qualquer permissão nova/alterada exige novo consentimento e invalida o estado `connected` até validação.
4. `MS_GRAPH_CLIENT_ID` e a credencial tornam-se configuração global de infraestrutura. `MS_GRAPH_TENANT_ID` não faz parte do contrato: o runtime Graph usa exclusivamente o tenant Microsoft registrado em `MicrosoftConnection`.
5. No V1, a credencial global fica em secret manager, com rotação, expiração monitorada e acesso mínimo; nunca gravar secret global no PostgreSQL. Certificado de CA ou workload identity/federated credential permanecem evoluções possíveis, sem mudar esse contrato.

## Onboarding e admin consent

O seed cria somente o `platform` e seu `admin@example.com` ativo, que fornece a fronteira de provisioning. Um admin desse tenant cria o customer inativo, os temas de Governance e o convite individual `role=admin`/`purpose=customer_bootstrap`, sem criar User ou membership do cliente. `role` (`admin`/`member`) e `purpose` (`customer_bootstrap`/`access`) são dimensões independentes; admins adicionais usam `admin/access`. O convite é de uso único, expira em 7 dias e sua URL é recuperável pelo iniciador autorizado enquanto pending; o scheduler o expira idempotentemente e elimina o ciphertext. Seu aceite cria/reutiliza User, cria membership `admin active` e preenche `tenants.activated_at` write-once atomicamente. O admin customer usa `purpose=access` para adicionar usuários ao próprio tenant. O consentimento Microsoft nunca cria, remove ou ativa essa autoridade local. Depois do aceite, o admin customer cria uma tentativa local de conexão vinculada ao tenant e a si próprio. Gerar `state` aleatório, opaco, de uso único, com TTL curto; salvar somente seu hash, intenção, retorno permitido e expiração. Não colocar tenant ID, permissões ou URL arbitrária em `state`. Não há criação self-service de tenant, registro público de usuário ou acesso por correspondência de domínio de e-mail.

Redirecionar para `https://login.microsoftonline.com/organizations/adminconsent?client_id={global-client-id}&redirect_uri={registered-callback}&state={opaque}` quando o admin escolher a authority padrão. O diálogo também permite informar exclusivamente um Microsoft Entra Tenant ID GUID; nesse caso, normalizar e guardar o valor como `expected_microsoft_tenant_id` na tentativa — nunca no `state` — e usar `https://login.microsoftonline.com/{tenant-id}/adminconsent`. Esse endpoint não recebe `scope`; `.default` continua sendo exclusivamente o scope do token app-only em runtime. `common` não é usado no onboarding. Callback é obrigatório mesmo no app-only: ele fecha o consentimento humano; não troca o modelo de token runtime.

No callback: validar HTTPS, rota registrada, `state` constante/uso único/TTL e correlação com tentativa; provar que o iniciador ainda possui membership `admin` no tenant da tentativa; tratar `error`, `error_description`, `error_codes`, `trace_id` e `correlation_id` sem expor detalhes ao usuário. O `tenant` recebido é somente candidato Entra e não instala `CurrentTenant` nem contexto RLS. Quando a tentativa tiver `expected_microsoft_tenant_id`, exigir igualdade antes de qualquer I/O Graph; divergência, erro ou cancelamento encerram somente aquela tentativa com razão sanitizada. Em sucesso, fazer uma verificação server-to-server contra a authority explícita: obter token app-only, chamar `GET /organization?$select=id` e exigir `organization.id` igual ao candidato antes de marcar `connected`. O access token é opaco para a aplicação e não é decodificado para comparar `tid`. Após a prova, gravar o vínculo somente se `microsoft_tenant_id` ainda não estiver associado a outro tenant interno; a unique global, o lock/idempotência e o tratamento de colisão impedem corrida e não revelam a organização já conectada. Registrar o conjunto esperado de app roles/permissões e a hora da prova.

Estados recomendados: `pending_consent`, `verifying`, `connected`, `consent_required`, `revoked`, `error`, `disconnected`. A classificação considera a etapa (`token_endpoint` ou Graph), HTTP status, código AADSTS/Graph sanitizado e `Retry-After`: `global_credential_failure`, `consent_required`, `permission_required`, `connection_invalid`, `throttled`, `transient` ou `unknown`. `401` ou `403` isolados não definem uma transição. Incidente de credencial global não altera arbitrariamente cada connection; consentimento/revogação comprovados são estado da connection. Desconectar desativa a conexão, cancela sync futuro e revoga localmente o vínculo; os dados históricos são mantidos até exclusão administrativa explícita, cujo fluxo fica fora do V1, e nunca são apagados automaticamente nesta fase.

## Runtime Laravel e Graph

Substituir `TenantContext` atual por dois contratos explícitos:

```php
interface CurrentTenant { public function tenant(): OrkestriaTenant; }
interface MicrosoftConnectionResolver { public function connectedFor(OrkestriaTenant $tenant): MicrosoftConnection; }
interface GraphClientFactory { public function forConnection(MicrosoftConnection $connection): GraphClient; }
interface MicrosoftConnectionVerifier { public function verify(MicrosoftConnectionAttempt $attempt, string $candidateMicrosoftTenantId): VerifiedMicrosoftOrganization; }
```

No V1, middleware resolve um tenant por vez pela associação local explícita e prova membership/capacidade antes de instalar `CurrentTenant` ou contexto RLS. Não há seletor, troca de tenant, descoberta por domínio de e-mail ou identificador de tenant na request; essa limitação de front não proíbe multi-membership futuro no schema. Candidato não é contexto autorizado. Controllers recebem o `CurrentTenant`, nunca string da request. O callback resolve a tentativa pelo `state` no control plane e segue a regra específica de validação do iniciador. Em command/job, receber `orkestriaTenantId` e `microsoftConnectionId` serializados, recarregar ambos, validar que o tenant é `customer` e que a connection está `connected`, e só então abrir contexto delimitado. `GraphClientFactory::forConnection()` aceita somente connection `connected` de customer, valida vínculo, UUID Entra e credencial global e instancia o `ClientCredentialContext` com `connection.microsoft_tenant_id`, client ID/credential globais e escopo `.default`. `MicrosoftConnectionVerifier` é exclusivo de onboarding de customer e valida connection `pending`/`verifying` por token app-only e `/organization`; ele não reutiliza a factory de runtime. `config('services.microsoft_graph.tenant_id')` e qualquer tenant Microsoft global não fazem parte do contrato; runtime, bootstrap, seed e onboarding usam exclusivamente a `MicrosoftConnection` ou o tenant candidato explicitamente validado no fluxo.

O administrador do `platform` opera exclusivamente o control plane: cria customer e seu primeiro `admin/customer_bootstrap`, sem acesso operacional aos dados do customer. Ele pode adicionar outro admin platform por `admin/access`. Memberships são `active` somente no aceite (ou no seed platform), e só são `revoked` por cancelamento explícito de acesso. O admin customer, ativado antes do onboarding Microsoft, pode conectar/desconectar Microsoft 365, alterar configurações e administrar memberships somente do próprio tenant; usuários adicionais são explicitamente convidados com `purpose=access`, nunca por domínio de e-mail ou registro público. `member` acessa as capacidades operacionais permitidas no tenant, sem administrar sua fronteira de segurança. Policies/Gates avaliam essa capacidade mínima sem introduzir package de roles. A entrega usa fresh deployment: não importa configuração ou dados da instalação single-tenant anterior.

## Alternativas consideradas

| Alternativa | Decisão | Motivo |
| --- | --- | --- |
| Uma App Registration multitenant + credencial global | recomendada | Modelo pedido, sem segredos por cliente e consistente com service principal por organização. |
| App Registration por organização | rejeitada | Aumenta operação, rotação e onboarding; só reconsiderar se houver isolamento/regulação que exija credenciais do cliente. |
| Delegated permissions | rejeitada | Contraria requisito app-only e acopla sync a usuário/sessão. |
| `common`/`organizations` para token client credentials | rejeitada | Microsoft orienta authority explícita de tenant em daemon apps. |
| `spatie/laravel-multitenancy` 4.x | não adotar no V1 | Banco único e sync explícito por tenant+connection não justificam tasks do package hoje; preservar a porta `CurrentTenant` para possível adoção futura. |
| `spatie/laravel-permission` 8.x | não adotar no V1 | Há apenas as capacidades mínimas `admin`/`member` na membership; um package de RBAC é desproporcional. |
| RLS PostgreSQL | adotar no V1 multi-tenant | Barreira obrigatória para o tenant data plane, complementar a control plane, contratos, constraints, testes e contexto explícito. |
